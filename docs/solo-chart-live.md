# 单人谱面演出

MFA 任务列表中选择 **🎼 单人谱面演出**。该任务默认关闭，使用 MFA 已连接的 MuMu 控制器，按照本地 SUS 的时刻执行多点触控。每局体力消耗由用户设置，关闭游戏 AUTO、采用轻量背景；原有「自动演出」仍使用游戏内 AUTO LIVE。

## 任务选项

| 选项 | 含义 |
| --- | --- |
| 选曲方式 | 当前歌曲、随机选取或指定歌曲搜索；指定模式填写本地目录中的完整曲名。 |
| 谱面难度 | EASY、NORMAL、HARD、EXPERT、MASTER、APPEND，默认 EASY。当前歌曲没有所选难度时停止，不回退到其他谱面。 |
| 演出次数 | 1–999，默认 1；每局从主页重新选曲。 |
| 体力不足时使用道具 | 默认关闭；可选小饮料（每瓶 +1）或大饮料（每瓶 +10）。 |
| 每次回复饮料数量 | 1–99 瓶，默认 1；每次体力不足时按所选种类回复指定瓶数，没有任务累计瓶数上限。 |

**MFA 设置 → 演奏设置** 保存谱面触控偏移（-300 到 300 ms）、每局体力消耗检测
（沿用游戏数量或 0–10）、引擎与校准配置使用选项。正偏移推迟触控，负偏移提前。

环境要求为日服、横屏 1280×720、240 DPI。任务开始检查连接、截图和前台包名。游戏流速保持用户设置；每次任务首次准备时以两张截图确认一次消耗设置，成功保存后后续局沿用任务快照，重新开始任务才再次检测。任务结束后保留用户选择的消耗量。沿用模式读取游戏当前设置，不调整消耗滑条；指定模式逐次确认加减按钮，避免去抖吞掉输入。每局仍检查实际可用体力、AUTO 关闭和轻量背景。

2026-10-07 本机一次消耗设置验收完成两个准备阶段：消耗菜单只打开、保存各一次，第一阶段实际确认 5 体力设置，第二阶段沿用任务快照；两阶段分别确认可用体力为 9、足够当前消耗。未开演、未消耗体力、未用药，确认回主页且保存设置不变。本次范围仅为准备与任务快照，完整连续演出、校准共享及协力恢复路径仍须独立验收。

消耗大于 0 时，开演前读取顶部当前体力并连续两帧确认。体力充足直接开演；不足且自动用药关闭时停止，保持原定消耗量。开启自动用药时复用「自动演出」的道具流程：同页复位小／大饮料滑条，按设置 N 瓶点击指定饮料加号 N 次，等待「决定」启用，一次决定后只点击一次二次确认 OK；不逐瓶返回重进；体力更新后用 ESC/BACK 关闭完成提示。只读取实际体力，不识别饮料库存或已选瓶数，不使用水晶或广告。

AUTO、单人与协力按批核对实际体力：用药前读数无法确认时不使用饮料，OK 后须连续两帧读到相同且达到本批预期增量的数字才确认到账（小药 +N、大药 +10N）；不能把只增加 1 记成已用 N 瓶，也不使用像素均值判断。整批到账先保存 `recovery.completed_bottles`、当前体力和读数，再关闭提示；后续确认或关闭失败时保留已用数量，不重做整批。未足额确认时保存实际前后读数和预期增量，等待用户处理，不追加用药。

一批指定瓶数用完仍不足以满足每局消耗时停止，提示调整回复瓶数；不自行追加瓶数或降低每局消耗。后续局再次缺体力时仍按相同设置回复。用药后保持 AUTO 关闭，由本地 SUS 驱动演奏。

本机已独立验收同页五瓶小药：加号五次、一次决定、一次 OK，体力 5→10，两帧到账一致，五瓶进度先持久化再一次 BACK 关闭通知，并确认回主页。此次在单人准备页执行共用 Navigator，没有开演；沿用协力已保存的小药五瓶设置作为输入，演奏设置及各任务种类／瓶数保持不变。大药多瓶、AUTO 与协力任务实际触发仍须独立验证，未新增协力演出。

## 本地资源与歌曲确认

先通过 **MFA 设置 → 谱面管理** 同步日服库，详细说明见 [日服在线谱面库](sekai-chart-repository.md)。任务运行期间只读本地数据，不下载谱面。

准备页将倾斜封面透视校正后，同时匹配本地封面与日文标题，并读取实际难度。加载前检查谱面身份、路径和 SHA256。点击开始后持续采样，经过加载场景直到开场身份及难度确认，再与准备页身份比对；这两个页面各自独立确认，不额外要求开场页连续两帧命中。等待最多 120 秒，若未确认身份就进入演奏页则立即停止，期间不派发谱面输入；身份确认后才进入首音同步。

开场文字淡入、难度条移动时继续取帧重试；对白字提取后裁剪完整字形，准备页额外去掉封面底边，保留日文浊点。封面与标题是独立通道：封面要求整图分数至少 0.85、候选差值至少 0.06，整图不足时可用带覆盖约束的特征配准确认；标题单独确认要求 OCR 置信度至少 0.85、标题相似度至少 0.90，且与次选相差至少 0.08。任一明确且唯一的通道可提供身份，两个明确通道冲突则拒绝使用。实际难度不符或缺少谱面时停止。报告 `identity_checks` 保存两阶段的两个通道证据；截图编码和 MFA 嵌套日志推迟处理，避免阻塞同步。

用户提供的三张参考截图中，准备页与最终封面对应本地歌曲 **186「初音天地開闢神話」MASTER Lv.33**。Loading 页面只作为流程证据，不能单独决定歌曲身份。

## 演奏与停止

SUS 解析覆盖 BPM 与拍号变化、WAVEOFFSET、普通／金色音符、trace、方向 flick、长条节点及 Bézier 控制点。十二条演奏轨道按照音符宽度计算触控中心；技能、fever、装饰 guide 和擦除标记不直接派发输入。长条使用独立触点，曲线每 20 毫秒采样，最多十个并发触点。

触控计划版本 4 区分长条判定点与路径节点：有短音符附着、没有方向的可见点沿实际曲线取位置，不使用其占位坐标切断曲线；带缓动方向或没有短音符的节点继续定义路径。这与 [SUS 渲染器的节点处理](https://github.com/Team-Haruki/pjsekai-scores-rs/blob/main/src/notes/slide.rs) 及本机失败帧对应，改变触控计划后原自动校准配置失效，用户手动偏移保留。

离线滑条采样候选提供 `compile_touches(chart, sample_slide_nodes=True)`：保留版本 4 的原网格，额外在真实内部路径节点取 `slide_x` 坐标，跳过 Bezier 控制点与占位判定点，并对 1 ns 内重复时间去重。
候选标识为 `SLIDE_NODE_TOUCH_PLAN_VERSION = 5`；正常 `TOUCH_PLAN_VERSION` 仍为 4，MFA、设备入口、运行设置与校准环境均未接入此候选，默认输入保持原样。
运行 `python scripts/replay_slide_sampling.py <谱面.sus> --baseline-touch-plan <touch-plan.jsonl> --output <对比.json>` 可离线核对原计划、新增 MOVE 和版本；不连接设备。
该候选只证明急转弯节点能及时采样，MISS 是否改善仍须独立实机验收。

开场仅根据谱面的第一音建立时钟锚点，记录实际下落轨迹并比较直线／透视模型的残差。慢截图链路下，在限定的首音位置与速度范围内，也可使用本机实测校验的透视模型从两帧提前同步；其他情况下要求至少三帧轨迹。图像时钟采用 screencap 请求开始时间，避免将 gzip 传输和 Agent 解码耗时当作拍摄时间。锚点建立后，音符输入全部来自 SUS，不实时识别后续音符。

同步版本 6 在候选模型残差相差不超过 1 像素时优先使用已实机验证的透视几何；顶端短轨迹不能凭亚像素级残差优势选择外推几十毫秒更早的指数模型。Trace 首音按三角箭头外框保留较高的轮廓，避免低流速时套用普通横条长宽比而漏掉首音、误取后面的音符；位置、宽度及高度门槛保留。质量、样本与启动余量门槛保留，明显较差的透视候选不会覆盖更好的拟合。报告 `start_anchor.fit` 记录所有合格模型及选择原因，版本变化使旧校准配置失效，手动偏移保留。

逐条触控引擎以固定手动偏移补偿设备输入延迟。Native 引擎接入滚动设备脚本、执行回执与未来命令成本补偿，校准任务按演奏设置中的体力数量取得正式验证的偏移配置；参见 [Native 与校准](native-calibration.md)。2026-10-05 起校准以实际 FAST/LATE（SLOW）平衡为目标，不因 MISS 等其他判定单独拒绝，仍保留 LIVE CLEAR、音数匹配和完整输入释放门槛；历史旧精度标准的验收记录不自动产生新配置。本机旧链路的 +30 ms 不能作为其他链路的通用校准值。

Maa Agent 的反向 RPC 按顺序执行，页面截图只安排在无活动触点且距下一动作超过 850 毫秒的空档，避免并发通信阻塞和截图占用触控时段。因此密集谱面中页面异常的自动发现可能推迟至下一个安全空档；MFA 用户停止请求仍持续检查。

触控回执失败、调度落后超过 180 毫秒、演奏页消失或用户停止时释放本轮触点。输入异常会尝试采集最终判定并保留实际数据，失败局不计入完成次数。结算只用右下角安全像素 `(1279, 719)` 加速动画及 ESC／Android BACK 返回，不识别或点击结算按钮；每次 BACK 前复查主页、标题页和判定数字，避免跳过判定页或从主页继续返回。

单人及一键演奏页由固定 LIFE 标签与暂停按钮共同确认，任一仍在就保留输入；单帧缺失先等待，连续两张有效画面均缺失才中断，纯黑／纯白帧不参与缺失计数。协力采用独立的正向页面证据和低频保护规则，见[协力演出](cooperative-chart-live.md)。生命零与 LIVE FAILED 继续单独判断。报告 `playfield_monitor` 保存匹配分数、连续缺失数和暂停按钮漏识别时的生命栏确认次数。

## 判定记录

部署目录的 `debug/solo-chart-runs/` 包含每局独立目录及 `results.csv` 汇总。每局 `report.json` 保存歌曲与难度、资源 SHA256、请求与实际体力消耗、回复设置和实际回复证据、首音同步样本、派发延迟、完成状态及实际判定；首次确认的 `bonus.png` 保存消耗页，后续局的 `bonus.confirmation_source=task_snapshot` 和 `source_report` 指向本任务首次确认，不伪造新读数或截图。`recovery-after.png` 保存实际用药后的准备页，`result.png` 保存读取判定时的页面。

每局还默认保存 [演奏轻量 trace](performance-trace.md)，复用原有保护观察与逐动作派发数据，覆盖整曲并关联 Native 回执；输入清理后才写盘，记录失败不会中断演出。一键入口复用同一记录方式。

完整派发输入并确认触点释放后，以本局曾见到的固定 LIFE 标签在两张有效画面中连续消失确认演出结束。标签不包含生命数字和条带，零生命不会被当成消失；纯黑／纯白转场先等待，最多等待结算及返回主页 120 秒。LIVE CLEAR 作为辅助证据，普通演出漏识别该文字仍可推进结算；只有实际识别到它才记录 `live_status=cleared`，否则记录 `ended` 和 `end_detection`。自动校准仍要求实际 LIVE CLEAR。

必须取得两帧一致的 **PERFECT / GREAT / GOOD / BAD / MISS** 后才能认定成绩已记录，并与本地元数据音符总数核对。无法读取全部判定或总数不一致时，保留实际数据、截图及 `settlement_warning`，正常返回主页后继续剩余演出次数。未完整记录的局不增加完整记录计数，也不额外补演；`performance_completed` 与完整成绩的 `completed` 分别记录。LIVE FAILED、生命零、输入／释放失败及无法恢复的连接或页面异常仍停止后续局。JSON 与 CSV 落盘后才更新进度。

- `perfect_rate` = PERFECT / 五种判定总数。
- `hit_rate` = (总数 - MISS) / 总数。
- COMBO、分数、FAST、LATE、FLICK 可读时一并记录；无法可靠读取的可选数字为 `null`，CSV 中为空。

这两个比例是明确定义的统计指标，不代表游戏官方加权准确率。截图、日志、索引、模型及谱面缓存均保持 Git 忽略。

## 离线 OCR

安装项目依赖后，准备 PP-OCRv5 的离线识别模型：

```powershell
python -m pip install -r requirements.txt
python scripts/setup-song-ocr.py
```

已有相同模型时可通过 `--source-dir "<模型目录>"` 本地复用；脚本检查 SHA256，已校验文件不会重复下载。来源为 [PaddlePaddle/PP-OCRv5_mobile_rec_onnx](https://huggingface.co/PaddlePaddle/PP-OCRv5_mobile_rec_onnx)，Apache-2.0。模型安装目录是 `resource/models/song_title_ocr/`，部署时复制模型，不重复复制谱面库。模型仍保持忽略，不随源码分发。

SUS 的格式依据 [SUS 规范](https://gist.github.com/kb10uy/c171c175ba913dc40a73c6ce69da9859) 及 [Project SEKAI 扩展说明](https://gist.github.com/YumYummity/49935bf74367712b6ba240474cb7ce22)。参考过 [ssm](https://github.com/kvarenzn/ssm) 的资源和触控方案；本项目没有打包该项目源码或运行程序。

```powershell

python scripts/test_solo_live.py --difficulty easy --count 1 --bonus-consumption 0 --recovery-mode off
```

独立验收入口默认 0 体力和关闭用药，`--engine native` 选择 Native，`--calibrate` 运行两局校准。
经用户授权后可显式传入 `--bonus-consumption 5 --allow-stamina-spend`；用药另需指定
`--recovery-mode`、`--recovery-count` 与 `--allow-item-use`，不会修改 MFA 保存的任务选项。
